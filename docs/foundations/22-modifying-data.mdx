# Modifying data: `INSERT`, `UPDATE`, `DELETE`, `RETURNING`

## First principles

Writes are **set-based**, like reads. One `UPDATE` changes *every* row its
`WHERE` matches — there's no loop, and no `WHERE` means **all rows**.

```sql
INSERT INTO t (a, b) VALUES (1, 2), (3, 4);      -- literal rows
INSERT INTO t (a, b) SELECT a, b FROM staging;   -- rows from a query
UPDATE t SET b = b * 2 WHERE a > 10;             -- every matching row
DELETE FROM t WHERE created_at < now() - INTERVAL '1 year';
```

**`RETURNING`** turns a write into a query: it returns the affected rows (with
their *final* values, including defaults and triggers). Great for getting a
generated id back, or feeding a pipeline.

```sql
INSERT INTO products (name, price) VALUES ('Pen', 3) RETURNING product_id;
UPDATE products SET price = price * 1.1 WHERE archived = false RETURNING product_id, price;
```

**`UPDATE ... FROM`** / **`DELETE ... USING`** join to other tables to decide
what/how to change:

```sql
UPDATE products p SET price = p.price * (1 + b.pct/100)
FROM price_bumps b WHERE b.product_id = p.product_id;
```

**Data-modifying CTEs** run each write **once** and let you chain them:

```sql
WITH archived AS (
  UPDATE products SET archived = true WHERE price < 5 RETURNING *
)
INSERT INTO audit (msg) SELECT 'archived ' || name FROM archived;
```

## The mechanism

```mermaid
flowchart LR
    W["UPDATE ... WHERE p"] --> M["find all rows where p is true"]
    M --> A["apply SET to each"]
    A --> C["constraints & triggers fire per row"]
    C --> R["RETURNING: emit final row values"]
```

## Build → Break → Fix → Why

:::tip 🔨 Build
Raise the price of one category, safely:

```sql
BEGIN;
UPDATE products SET price = price * 1.1 WHERE name LIKE '%lamp%' RETURNING *;
-- eyeball the RETURNING rows
COMMIT;   -- or ROLLBACK
```
:::

:::danger 💥 Break
Run the `UPDATE` with a typo'd `WHERE` (or none) outside a transaction:

```sql
UPDATE products SET price = price * 1.1;   -- every product, committed instantly
```

In autocommit mode this is **done** the moment you hit enter — no undo.
:::

:::note 🔧 Fix
- Wrap risky writes in `BEGIN; ... ROLLBACK;` and inspect with `RETURNING` /
  `SELECT` before you `COMMIT`.
- `SELECT` the `WHERE` first: run `SELECT * FROM products WHERE <predicate>`, then
  reuse the exact predicate in the `UPDATE`.
- Least-privilege DB users, backups, and `--single-transaction` for scripts.
:::

:::info 🧠 Why it behaved that way
An `UPDATE`/`DELETE` is one set-based operation over every row matching `WHERE`.
Omit `WHERE` and the matching set is the whole table. Outside an explicit
transaction each statement auto-commits, so there's no rollback point. Inside
`BEGIN ... COMMIT` the change is invisible to others and reversible with
`ROLLBACK` until you commit.
:::

## Pitfalls & idioms

- **No `WHERE` = all rows.** Habitually write the `WHERE` first.
- Test destructive writes in a transaction; `RETURNING *` to verify before
  `COMMIT`.
- `UPDATE ... FROM` with a join that matches a row **more than once** →
  non-deterministic result (Postgres picks one arbitrarily). Make the join
  unique, or aggregate the source first.
- `RETURNING` sees final values (defaults, `BEFORE` triggers, computed columns).
- Bulk load: `INSERT ... SELECT` or `COPY`, not thousands of single-row
  `INSERT`s.
- `DELETE` that should be reversible → a `deleted_at timestamptz` soft-delete
  column instead (Backend track).
- Data-modifying CTEs: the sub-statements all see the **same snapshot** and run
  once; order of side effects between them isn't guaranteed, so don't have two
  CTEs write the same row.
