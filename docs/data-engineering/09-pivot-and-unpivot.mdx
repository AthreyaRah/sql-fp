# Pivot & unpivot

## First principles

- **Long / tall / narrow**: one row per observation — `(region, month, value)`.
  Flexible, easy to filter/aggregate/extend, and the right shape to **store**.
- **Wide / crosstab**: one row per entity, one column per category —
  `(region, jan, feb, mar)`. The shape a **report or a spreadsheet** wants.

**Pivot** = long → wide. **Unpivot** = wide → long. Both are query-time
reshaping; you keep the data long.

### Pivot (long → wide)

Conditional aggregation — one aggregate per output column:

```sql
SELECT region,
  sum(revenue) FILTER (WHERE month = 'Jan') AS jan,
  sum(revenue) FILTER (WHERE month = 'Feb') AS feb,
  sum(revenue) FILTER (WHERE month = 'Mar') AS mar
FROM sales_long
GROUP BY region;
```

`FILTER (WHERE ...)` is the clean modern form; older code uses `sum(CASE WHEN
month='Jan' THEN revenue END)`. The `tablefunc` extension's `crosstab()` does it
too, but you must declare the column list — no better than `FILTER` for a fixed
set.

**The column list must be known at query-write time.** SQL results have a fixed
column set, so a *dynamic* pivot ("a column per month, whatever months exist")
needs code that builds the SQL string, or returning `jsonb` and letting the app
spread it.

### Unpivot (wide → long)

`UNION ALL` one `SELECT` per source column, or `unnest` parallel arrays, or a
`LATERAL` + `VALUES`:

```sql
SELECT region, m.month, m.revenue
FROM sales_wide
CROSS JOIN LATERAL (VALUES
  ('Jan', jan), ('Feb', feb), ('Mar', mar)
) AS m(month, revenue);
```

## Build → Break → Fix → Why

:::tip[🔨 Build]
Store long (`sales_long`). Pivot for reports with `sum(x) FILTER (WHERE cat =
'...')` per output column. When the categories vary, `jsonb_object_agg` and let
the presentation layer spread it.
:::

:::danger[💥 Break]
Store data **wide** — a `metrics` table with columns `jan_2024, feb_2024,
mar_2024, ...`. Every new month is a schema migration; "revenue for Q1" is
`jan + feb + mar` (a formula you rewrite each quarter); "months where revenue
dropped" needs an unpivot before you can even ask; and the table has 60 nullable
columns.
:::

:::note[🔧 Fix]
- **Store long**, pivot at query time.
- Fixed, known category set → `FILTER` aggregation.
- Unknown/growing set → `jsonb_object_agg`, or generated SQL, or unpivot-then-
  process.
- Unpivot a wide source with `LATERAL (VALUES ...)` or `UNION ALL`.
:::

:::info[🧠 Why it behaved that way]
A SQL query's output has a **fixed column list** determined when the query is
parsed — so "a column per category" only works when you can name the categories
in the SQL. `FILTER` aggregation is just `GROUP BY` with a per-column predicate
on the aggregate. Long storage keeps categories as *data* (rows), which you can
add, filter, and aggregate without touching the schema; wide storage makes
categories *structure*, so every category change is DDL and every cross-category
question is arithmetic on column names.
:::

## Pitfalls & idioms

- `FILTER (WHERE ...)` over `CASE` inside the aggregate — clearer, and works for
  `count`, `sum`, `avg`, etc.
- `NULL` from a `FILTER` that matched nothing — `coalesce(..., 0)` if the report
  wants zeros.
- Dynamic pivot: `jsonb_object_agg` for an API; `crosstab()` (tablefunc) still
  needs a static column definition; a stored proc that builds `EXECUTE`
  `format(...)` for a truly dynamic result set.
- Unpivot: `UNION ALL` is portable; `LATERAL (VALUES ...)` is compact and does
  one table scan.
- Pivoting for a spreadsheet export is fine; pivoting *into storage* is the
  anti-pattern.
- `GROUPING SETS` ([foundations](/foundations/grouping-sets-rollup-cube)) adds
  subtotals to a pivot.
