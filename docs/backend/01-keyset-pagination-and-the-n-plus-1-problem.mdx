# Keyset pagination & the N+1 problem

Two query shapes an API serves constantly. Both look fine on a laptop with 100
rows and fall over at scale.

---

## Part 1 — Pagination

### First principles

`LIMIT 20 OFFSET n` asks the database to **produce the first `n + 20` rows in
order and throw `n` of them away**. Page 1 (`OFFSET 0`) is instant; page 5000
(`OFFSET 100000`) computes 100 020 rows to return 20. Cost grows with page
number, and under concurrent inserts rows **shift between pages** (you see a row
twice, or miss one).

**Keyset (seek) pagination** remembers the *last row you showed* and asks for
"the next 20 after this key":

```sql
-- page 1
SELECT post_id, title, created_at FROM posts
ORDER BY created_at DESC, post_id DESC
LIMIT 20;

-- next page: pass the last row's (created_at, post_id) as $1, $2
SELECT post_id, title, created_at FROM posts
WHERE (created_at, post_id) < ($1, $2)          -- row-value comparison
ORDER BY created_at DESC, post_id DESC
LIMIT 20;
```

With an index on `(created_at DESC, post_id DESC)` every page is the **same
cost** — seek to the key, read 20, done. The trade-off: no random "jump to page
137" (you can only go next/prev), which is fine for infinite-scroll feeds and
most APIs.

The `(created_at, post_id)` **tuple** is essential: `created_at` alone isn't
unique, so you need the id as a tiebreaker, and the row-value comparison
`(a, b) < ($1, $2)` expresses "earlier timestamp, or same timestamp and smaller
id" in one sargable predicate.

### Build → Break → Fix → Why

:::tip 🔨 Build
Feed endpoint: `ORDER BY created_at DESC, post_id DESC LIMIT 20`, return the last
row's `(created_at, post_id)` as the `next_cursor`. Next call filters
`WHERE (created_at, post_id) < (cursor)`.
:::

:::danger 💥 Break
Ship `LIMIT 20 OFFSET (page-1)*20`. Page 1 is 2 ms. A power user on page 3000 is
900 ms and climbing; meanwhile new posts arrive, so their page 2 now shows a post
they already saw on page 1.
:::

:::note 🔧 Fix
Keyset. Order by a **unique tuple** ending in the primary key, index that exact
tuple + direction, and page with a row-value comparison. Expose an opaque
`cursor` string, not a page number.
:::

:::info 🧠 Why it behaved that way
`OFFSET n` has no shortcut — SQL defines it as "discard the first `n` rows of the
ordered result", so the engine must generate them. Keyset turns "the next page"
into a **range predicate** the index can seek to directly, so work is
proportional to page *size*, not page *position*. And because the cursor is a
real data value, concurrent inserts above it don't renumber anything.
:::

## Part 2 — The N+1 problem

### First principles

You fetch a list, then loop and fetch a related row per item:

```
posts = SELECT * FROM posts WHERE ... LIMIT 20;      -- 1 query
for p in posts:
    p.author = SELECT * FROM authors WHERE author_id = p.author_id;   -- 20 more
```

That's **1 + N** queries (here 21) for one screen. Each is fast, but the
round-trip latency stacks: 21 × 1 ms network = 21 ms of pure waiting, and it
scales with page size. ORMs do this silently on lazy-loaded associations.

**Fixes**, in order of preference:

1. **Join** — one query returns posts *with* author columns.
2. **Batch load** — `SELECT * FROM authors WHERE author_id = ANY($1)` with the 20
   ids, then stitch in code. (ORMs call this "eager loading" / `includes` /
   `selectinload`.)
3. **`json_agg`** — return the nested shape directly from SQL.

{`WITH page AS (
  SELECT post_id, author_id, title FROM posts
  ORDER BY created_at DESC, post_id DESC LIMIT 20
)
SELECT * FROM authors WHERE author_id = ANY (SELECT author_id FROM page);
-- the app joins page + authors in memory by author_id`}
</SqlRunner>

<SqlRunner title="return the nested shape from SQL with json_agg" setup={schema}>
{`SELECT a.author_id, a.name,
       json_agg(json_build_object('post_id', p.post_id, 'title', p.title)
                ORDER BY p.created_at DESC) AS recent_posts
FROM authors a
JOIN LATERAL (
  SELECT * FROM posts p WHERE p.author_id = a.author_id
  ORDER BY created_at DESC LIMIT 3
) p ON true
WHERE a.author_id <= 3
GROUP BY a.author_id, a.name
ORDER BY a.author_id;`}
</SqlRunner>

### Build → Break → Fix → Why

:::tip 🔨 Build
List endpoint does one `JOIN` (or one list query + one `WHERE id = ANY($ids)`
batch). Zero per-item queries.
:::

:::danger 💥 Break
Serialize `post.author.name` with a lazy ORM association and no eager-load hint.
The list endpoint issues 1 + page_size queries. It's invisible in dev (1 + 5),
then it's the p99 in prod (1 + 100) and the DB connection pool is saturated.
:::

:::note 🔧 Fix
- Prefer a `JOIN` when you need a few columns of the related row.
- Batch-load (`WHERE id = ANY(...)`) when the ORM makes joins awkward or you need
  whole related objects — this is `includes` / `prefetch_related` /
  `selectinload`.
- `json_agg` / `LATERAL` when the response is genuinely nested and you want the
  DB to shape it.
- Turn on your ORM's "raise on N+1" / query-count assertions in tests.
:::

:::info 🧠 Why it behaved that way
Each query has fixed overhead — parse, plan, network round-trip — that dwarfs the
work of fetching one row by primary key. N of them run **sequentially** (the loop
waits for each result before issuing the next), so latency is `N × round_trip`,
not `max`. A join does the matching **inside** the database in one pass over
indexes, with one round-trip, so page size stops mattering.
:::

## Pitfalls & idioms

- Keyset order key must be **unique** — always end it with the primary key.
  Index `(sort_cols..., pk)` in the exact directions the query uses.
- Row-value comparison `(a,b) < ($1,$2)` is one sargable predicate; the expanded
  `a < $1 OR (a = $1 AND b < $2)` is equivalent but the planner may not index it
  as well — prefer the tuple form.
- Keyset can't do "jump to page N" or "total pages" cheaply. If the product needs
  that, keep `OFFSET` for shallow pages and cap it, or maintain an approximate
  count.
- N+1 also happens on **writes** (insert children in a loop) — batch with
  `INSERT ... SELECT` / multi-row `VALUES`.
- A join that fans out (`authors` → many `posts`) inflates the parent columns —
  aggregate or use `LATERAL` + `LIMIT` per parent.
- `EXPLAIN ANALYZE` a keyset page and confirm it's an `Index Scan` with a tiny
  `actual rows`, not a `Sort`.
