# Reading EXPLAIN plans & query optimization

A worked case: **"a customer's recent paid orders"** — the kind of query behind a
"My Orders" page. It's slow. We'll read the plan, fix it, and confirm.

## The query

```sql
SELECT o.order_id, o.total, o.created_at
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE c.customer_id = 12345
  AND o.status = 'paid'
  AND o.created_at >= now() - INTERVAL '90 days'
ORDER BY o.created_at DESC
LIMIT 20;
```

Fresh schema, only primary-key indexes. Run `EXPLAIN (ANALYZE, BUFFERS)` and you
get something like this (numbers scale with table size — the *shape* is the
point):

```
Limit  (actual time=9.4..9.4 rows=20 loops=1)
  ->  Sort  (actual time=9.4..9.4 rows=20 loops=1)
        Sort Key: o.created_at DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Nested Loop  (actual time=0.1..8.9 rows=300 loops=1)
              ->  Index Scan using customers_pkey on customers c  (rows=1 loops=1)
              ->  Seq Scan on orders o  (actual time=0.1..8.4 rows=300 loops=1)
                    Filter: (customer_id = 12345 AND status = 'paid' AND created_at >= ...)
                    Rows Removed by Filter: 49700
        Buffers: shared hit=410
```

**The tells:**

- `Seq Scan on orders` + `Rows Removed by Filter: 49700` → a selective predicate
  with no supporting index.
- `Sort` on `created_at DESC` → could be free if the index were ordered that way.
- `Nested Loop` is fine here — the outer side is genuinely 1 row.

## The fix

```sql
CREATE INDEX idx_orders_cust_status_created
  ON orders (customer_id, status, created_at DESC);
ANALYZE orders;
```

Column order: **equality columns first** (`customer_id`, `status`), then the
**range/sort column** (`created_at`). Now the planner can seek to
`(12345, 'paid', <now>)` and walk backwards in `created_at` order — the `WHERE`
*and* the `ORDER BY` *and* the `LIMIT` are all served by one index range scan.

New plan:

```
Limit  (actual time=0.05..0.09 rows=20 loops=1)
  ->  Index Scan using idx_orders_cust_status_created on orders o
        Index Cond: (customer_id = 12345 AND status = 'paid' AND created_at >= ...)
      (actual rows=20 loops=1)
  Buffers: shared hit=6
```

~9 ms → ~0.05 ms.  410 buffers → 6.  No `Sort`.

## Build → Break → Fix → Why

:::tip[🔨 Build]
`EXPLAIN (ANALYZE, BUFFERS)` the endpoint query with a **realistic** parameter.
Locate the node with the biggest `actual time × loops` or the biggest
`Rows Removed by Filter`. Index exactly that access path (equality cols, then the
range/sort col). Re-`EXPLAIN`. Confirm the `Sort` is gone and buffers dropped.
:::

:::danger[💥 Break]
"Optimize" by reading `cost=` and adding an index that makes the *estimate*
smaller, without `ANALYZE` timing. Or index each `WHERE` column separately
(`(customer_id)`, `(status)`, `(created_at)`) and hope the planner combines them
— it does a `BitmapAnd`, better than a Seq Scan but still no ordered scan, so the
`Sort` and a bigger heap fetch remain.
:::

:::note[🔧 Fix]
One **composite** index in the right column order beats three single-column
indexes for this query: it serves the filter and the order and lets `LIMIT` stop
after 20 rows. Add `INCLUDE (selected cols)` to get an Index Only Scan.
:::

:::info[🧠 Why it behaved that way]
The slow plan's `Seq Scan` existed because *no index's leading columns matched
the equality predicates*, so Postgres had to read every row and filter. The
`Sort` existed because the rows arrived in physical order, not `created_at`
order. A B-tree on `(customer_id, status, created_at DESC)` is physically sorted
by exactly that tuple, so a single descend-and-scan satisfies the `=` conditions
(prefix), the `>=` condition (range on the last key), and the `ORDER BY`
(the scan direction) at once — and `LIMIT 20` stops it after 20 leaf entries.
:::

## Pitfalls & idioms

- Read plans **bottom-up**; the leaf that reads the most rows / spends the most
  `time × loops` is your target.
- `Rows Removed by Filter: <big>` under a `Seq Scan` = missing index on that
  predicate.
- Composite index order: **`=` columns, then one range/sort column**. Match the
  `ORDER BY` direction (`DESC`) so no `Sort` node appears.
- `Index Cond` (used the index to seek) vs `Filter` (checked after fetching) —
  you want your predicates as `Index Cond`.
- `INCLUDE` non-key columns for an Index Only Scan; keep the visibility map fresh
  with autovacuum.
- Always `ANALYZE` after creating the index and after big data changes.
- Verify with `EXPLAIN ANALYZE`, not `EXPLAIN` — estimates lie, actuals don't.
- One targeted composite index usually beats several single-column ones **and**
  costs less on writes.
